# bmo-drive

独自の API を持つ単一のサービスとして動くファイルビューアです。管理者はこのマシンのドライブ、Garage、ノードの
ボリュームを「場所」として巡回できます。各オーナーはクォータ付きの自分専用の BMO ドライブを持ち、そこにあるものを
読み書きできます。トークンを持たない相手にファイルやフォルダを一つ渡す共有リンクと、閲覧者の会社のメンバーが
それを読めるようにするメンバー共有も備えています。バイナリにはサービスに加えて、コマンド `bmo-drive file share`、
クライアント、ハーネスプラグイン（MCP サーバー `bmo-drive mcp` と `bmo-drive` スキル）が含まれます。他のユニットには
すべて、`docs/api.md` に挙げたとおりそれぞれの API を通じてアクセスします。

## テスト

テストベッドの `personal-data` チェックが個人データのルール（`PERSONAL-DATA.md`）を守ります。リポジトリには次の
テストがあります。`tests/import.rs` は旧アーカイブの共有リンクの取り込みを、`tests/owners.rs` はオーナーと二つの
ブランチを検証します。各オーナーのドライブはそのオーナーだけのものであること、クォータがバイトの到着前に判定される
こと、マシンは管理者だけのものであること、共有リンクが両方のブランチで開けることです。`tests/members.rs` は
メンバー共有を検証します。メンバーと共有したファイルやフォルダはそのメンバーだけが読め、共有を終えると再び読み取りが
拒否されます。`tests/console.rs` はコンソールフェイスを検証します。サービスが返すマニフェストを、`client/vendor/` に
あるリリースに対して bmo-ui 自身の読み方で読み（bmo-console-face が Bun で実行）、フェイスがコンソールの認証情報に
つながっていること、それ以外のすべてのルートをドライブ自身が守っていることを確かめます。`tests/links.rs` は
ボリューム上のリンクを検証します。自分自身へ戻るパスは拒否され、隣のフォルダへのリンクは一度だけ辿られ、各リンクの
ターゲットが一覧に出て、フォルダの zip はリンクで終わります。`tests/screen.rs` は Files 画面を検証し、そのモジュールも
同じく Bun で実行します。画面がどこで開くか、場所の記憶、オーナーに共有されたもののブランチ、そして各共有がメンバー
自身の経路で読まれる読み取り専用の場所であることです。`cargo test` でこれらすべてが走ります。バンドルはブラウザ
テストを `client/tests/` に持っています。Files 画面はそこにある小さな Nuxt ホストの中で単独で動き、バンドル自身の
文言とともに開発サーバーで配信され、サービスのスタンドインを相手に Chromium で操作されます。
`tests/browser/files-upload.test.ts` は開いたフォルダにファイルをドロップ・ペーストし、ペースト時にブラウザが名前を
付ける画像を貼り付け、名前変更欄に貼り付け、画面上でコピーした項目を貼り付けます。
`tests/browser/files-view.test.ts` は広いウィンドウとスマートフォンの幅で、ツールバーから表示を選びます。バンドルの
チェックである `client/` 内の `bun run check`（固定されたインストール、型チェック、ブラウザテスト）がこれらと並びます。
`docs/inventory.md` には旧来の挙動を守っていたテストが列挙されています。

## 構成

| フォルダ | 内容 |
|---|---|
| `src/` | サービス、コマンド、クライアント、MCP サーバー。一つのクレートをモジュールに分けたもの |
| `migrations/` | ストア。テーブルを順に作るステートメント |
| `skills/` | `bmo-drive` スキル。MCP サーバーと対になるハーネスプラグインのもう半分 |
| `client/` | コンソールプラグインバンドル：Files 画面とファイル共有ページ。独立したプロジェクトで、ビルドは `client/console/` にある |
| `deploy/` | サービスのユーザーユニットと、デプロイが公開するアプリ宣言 |
| `docs/` | サービスが何をするかの正規の記述と OpenAPI ドキュメント |
| `tests/` | 現時点で揃っている挙動テスト |

ルートには Cargo マニフェスト、`VERSION`、`testbed.toml`、`install.toml`、`rustfmt.toml`、`CLAUDE.md`、`PERSONAL-DATA.md`、
`korean-ledger.json`、`settings.toml`、`settings.local.toml.example`（デプロイが用意するローカル設定の例）、
`LICENSE` があります。

## コンソールプラグインバンドル

`client/` には bmo-ui の上に作った Files 画面とファイル共有ページがあります。bmo-ui のコンソールプラグイン契約
（bmo-ui の `docs/console-bundles.md`）に沿ったバンドルで、その中でこのサービスが選んだことは `docs/api.md` の
「The console face」にあります。文言は独自の言語パック `client/i18n/` にロケールごとに一ファイルずつ、`drive.*` の下に
置かれ、`docs/api.md` の拒否コードごとに `drive.error.<code>` があります。

- **ビルド。** `bun run bundle` は bmo-ui のバンドルビルドで画面のソースから `client/dist/` を作ります。このビルドは
  コンソールが共有するライブラリをバンドルに含めず、バンドルの土台となるレイヤーを書き出します。成果物は、二つの
  ページのルートをデフォルトエクスポートに持つモジュール `bundle.js`、画面がレイヤーのトークン上で使うユーティリティ
  クラスを収めたスタイルシート `bundle.css`、ロケールをキーとする一つのオブジェクトにまとめた言語パック
  `words.json`、そして `layer.json` です。ページが import せずに使うコンポーネントや Vue・Nuxt の関数はビルド時に
  import され、ビルドは `client/console/` にあります。デプロイはリリースごとにこのフォルダをビルドし、サービスは
  マニフェストとともにそのファイルを返します。
- **レイヤー。** `client/vendor/` には bmo-ui のリリースコマンドが書き出したままの bmo-ui リリースファイルがあり、
  bmo-chat の `shared-versions.toml` が固定しているものと同じです。バンドルはこれに対してインストール、ビルド、型
  チェックされます。コンポーネントライブラリはそのリリースが指定する正確なバージョンに固定され、インストール時に
  レイヤー自身のパッチ（プリミティブとアイコンを含む）が適用されます。パッチは `client/patches/` にあり、それぞれが
  指定した正確なバージョンにのみ適用されます。`client/` の Nuxt 設定は型チェックのためだけのものです。
- **型。** サービスの応答に対する画面側の型は、`bun run api` で `docs/openapi.json` から `client/shared/openapi.ts`
  に生成されます。

## ドキュメント

| ドキュメント | 内容 |
|---|---|
| `docs/files.md` | ファイルビューア：マシン、場所、フェンス、読み取り、変更、保護された場所、共有リンク、メンバー共有 |
| `docs/api.md` | ルート、応答と拒否、イベント、コマンド、ハーネスプラグイン、クライアント、他ユニットの呼び出し、設定 |
| `docs/openapi.json` | 同じ契約の機械可読版。`bmo-drive openapi` で生成 |
| `docs/inventory.md` | このリポジトリが旧リポジトリから引き継いだもの。各セットの件数と出所 |
| `PERSONAL-DATA.md` | このリポジトリに決して置いてはならないもの（人の名前、住所、パス、デバイスやネットワークの情報、ルームのメンバーや会社の情報、実際の会話の一行）と、それを守るチェック |

## バージョン

`VERSION` はリポジトリのバージョンであり、クレート自身のバージョンでもあります。どのように上がるかは `docs/api.md`
の「Versions」に記載されています。
